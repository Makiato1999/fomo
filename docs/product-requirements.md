# 双语术语知识图谱：第一阶段产品需求文档

> 状态：Draft  
> 版本：v0.2  
> 日期：2026-11-21

## 1. 产品概述

本产品不是传统笔记工具，而是一个以“专业术语”为基本单位、由 AI 辅助构建的个人双语知识图谱。

用户每次只需输入一个关键词。系统先检查错字、别名和规范名称，再判断具体行业语境；语境明确时自动联网验证并生成节点，只有明显歧义会改变专业含义时才请求用户选择。节点包含术语中英文、所属领域与具体范围、双语解释、案例、创建日期和字段级来源，并被编排进相关知识图谱。

系统还可以根据已确认的节点推导出同领域中可能需要补充的术语，以不同颜色显示为“未点亮节点”，帮助用户了解当前知识版图、上下游关系和下一步学习方向。

## 2. 产品目标

第一阶段需要解决以下问题：

1. 降低记录门槛：用户不需要组织笔记结构，每次只需输入一个想到的术语。
2. 规范专业术语：检查错字、别名和非首选表达，并在具体行业语境中确认规范名称。
3. 建立双语认知：提供经过行业语境校验的中文术语和专业英文表达，为中文理解及英文工作环境服务。
4. 自动结构化知识：为每个术语生成一致、可检索、可修订的节点内容。
5. 呈现知识关系：自动识别概念之间的前置、后续、组成、依赖、对比等关系。
6. 暴露知识缺口：用“未点亮节点”提示同一知识范围内尚未建立的关键概念。

## 3. 非目标

第一阶段暂不包含：

- 富文本笔记、日记或长文写作；
- 多人协作、公开分享和社交功能；
- 复杂的图谱手工排版；
- 自动判断用户是否真正掌握某个概念；
- 大规模题库、考试或完整学习管理系统；
- 将宽泛标签体系作为主要组织方式。

## 4. 核心概念

### 4.1 输入（Input）

用户每次提交一个关键词，例如“交收”“日切”或“最终一致性”。第一阶段不从长句或批量文本中提炼多个术语。

原始输入应被保留，以便追溯节点来源和后续重新分析。

### 4.2 规范术语（Normalized Term）

系统在具体语境中对用户输入进行规范化，检查错字、别名、缩写和行业常用表达。

语境明确时系统自动继续，不增加无必要的确认步骤。满足以下任一情况时才暂停并请求用户选择：

- 同一中文词在多个行业中具有不同定义；
- 不同语境对应不同英文术语；
- 输入词与推荐规范名称可能不是简单错字关系；
- 不同地区或市场的定义存在实质差异；
- 最高语境判断置信度低于配置阈值。

### 4.3 已点亮节点（Confirmed / Lit Node）

由用户输入或从建议节点点亮后创建的正式知识节点。它代表“用户希望纳入个人知识图谱”，不等同于“用户已完全掌握”。

### 4.4 未点亮节点（Suggested / Unlit Node）

由 AI 根据已确认节点和领域知识补充的相关概念。它们只显示精简信息，不直接写入用户的正式节点库。用户点击并确认后，系统再补全内容并将其点亮。

建议使用清晰的视觉差异：

- 已点亮：主色、实线边框；
- 未点亮：低饱和色、虚线边框或较低透明度；
- 正在生成：加载状态；
- 待用户校验：警示色标记。

## 5. 核心用户流程

### 5.1 创建节点

1. 用户在全局输入框输入一个关键词。
2. 系统保留原始输入，并检查错字、别名、缩写和可能的规范名称。
3. AI 判断可能涉及的行业、系统或技术语境。
4. 语境明确时自动继续；存在会改变专业含义的明显歧义时，系统展示 2～4 个具体语境供用户选择。
5. 系统联网检索并交叉验证中英文术语、领域、范围和核心定义。
6. 系统生成完整节点字段；无法充分验证的内容标记为 `needs_review`，不伪造确定性。
7. 用户可以查看、编辑并保存节点。
8. 系统分析新节点与现有节点的关系并更新局部图谱。
9. 系统生成少量未点亮节点，提示可能需要补充的相关知识。

### 5.2 从图谱点亮建议节点

1. 用户点击一个未点亮节点。
2. 系统展示该术语被推荐的原因、与现有节点的关系及简要解释。
3. 用户选择“创建节点”。
4. AI 补全完整字段，用户确认后保存。
5. 节点转为已点亮状态，相关边和附近建议随之更新。

### 5.3 查看与修订节点

1. 用户从搜索结果、列表或图谱打开节点。
2. 系统展示双语术语、领域范围、解释、案例、关系和来源。
3. 用户可以编辑任何 AI 生成字段。
4. 用户可以要求 AI 针对单个字段重新生成，但系统不得覆盖用户修改而不提示。

## 6. 节点数据结构

每个正式节点建议包含以下字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | UUID | 是 | 节点唯一标识 |
| `termZh` | string | 是 | 领域内常用中文术语，如“证券交收” |
| `termEn` | string | 是 | 领域内常用英文术语，如“securities settlement” |
| `aliasesZh` | string[] | 否 | 中文别名、简称或易混称呼 |
| `aliasesEn` | string[] | 否 | 英文别名、缩写，如 CCP、DvP |
| `domainZh` | string | 是 | 具体领域，如“证券交易后处理” |
| `domainEn` | string | 是 | 对应专业英文，如“securities post-trade processing” |
| `scopeZh` | string | 是 | 更精确的知识范围，如“清算完成后的证券与资金最终转移” |
| `scopeEn` | string | 是 | 对应英文范围描述 |
| `definitionZh` | text | 是 | 中文长解释 |
| `definitionEn` | text | 是 | 专业英文长解释，不应只是机械直译 |
| `examplesZh` | text / object[] | 是 | 中文案例，可包含真实工作场景或简化示例 |
| `examplesEn` | text / object[] | 是 | 与中文语义一致的英文案例 |
| `createdAt` | datetime | 是 | 创建时间 |
| `updatedAt` | datetime | 是 | 最近更新时间 |
| `sourceInput` | string | 是 | 触发节点创建的用户原始输入 |
| `status` | enum | 是 | `confirmed`、`suggested`、`needs_review` |
| `confidence` | number | 否 | AI 对术语及翻译判断的置信度，仅用于提示 |
| `evidence` | object[] | 否 | 术语校验所依据的来源名称、链接、访问日期和支持内容摘要 |
| `userEditedFields` | string[] | 否 | 标记用户手工修改过的字段，防止 AI 静默覆盖 |

### 6.1 领域与范围的约束

领域不能使用“金融”“计算机”“技术”等过于宽泛的类别。应尽量定位到能够解释该词具体语境的层级。

示例：

| 不合格 | 合格领域 | 合格范围 |
| --- | --- | --- |
| 金融 | 证券交易后处理 / Securities Post-Trade Processing | 清算完成后的证券与资金最终转移 |
| 计算机 | 分布式系统 / Distributed Systems | 复制状态机中的一致性模型 |
| 数据库 | 关系型数据库事务处理 / Relational Database Transaction Processing | 并发事务的隔离级别 |

领域本身是节点的描述字段，而非第一阶段的自由标签。后续可以将稳定出现的领域提升为独立节点。

## 7. 关系数据结构

图谱边应具有明确语义，不能只记录模糊的“相关”。第一阶段支持以下关系：

| 关系 | 英文 | 示例 |
| --- | --- | --- |
| 前置流程 | `precedes` | 清算 → 交收 |
| 后续流程 | `follows` | 交收 → 对账或后续账务处理 |
| 属于 / 组成 | `part_of` | 证券交收 → 证券交易后处理 |
| 依赖 | `depends_on` | 交收 → 清算结果 |
| 实现 / 支持 | `enables` | DvP → 降低本金风险 |
| 对比 / 易混淆 | `contrasts_with` | 清算 ↔ 交收 |
| 上位概念 | `is_a` | 最终一致性 → 一致性模型 |
| 相关 | `related_to` | 无法归入以上类型时的兜底关系 |

每条关系至少包含：

- 起点与终点；
- 关系类型；
- 方向；
- 中文关系说明；
- 英文关系说明；
- 生成来源（AI 或用户）；
- 置信度；
- 是否已由用户确认。

同一组节点可根据知识性质形成流程图、依赖图或概念层级图，不强制所有内容都表现为树。系统默认采用有向属性图模型，并在界面上按当前领域自动选择较合适的布局。

### 7.1 三种知识视图

底层只维护一份统一的节点和关系数据，界面根据用户当前要解决的问题，将同一张图投影为三种视图。视图切换不复制节点、不修改关系，也不改变知识事实。

#### 关系图（Relationship Graph）

关系图用于回答：

- 这个概念和哪些概念有关；
- 它前后依赖什么；
- 有哪些容易混淆的概念；
- 当前局部知识中还缺少哪些节点。

关系图是产品的默认主视图。它以当前节点为中心，默认显示一层邻居，用户主动展开时最多显示到两层。当前节点位于视觉中心，已确认节点处于内圈，未点亮建议节点处于外围。系统应优先保证局部关系可读，不默认把整个知识库一次性展开。

#### 领域树（Domain Tree）

领域树用于回答：

- 这个领域整体由哪些部分组成；
- 当前概念处于哪个层级；
- 哪些知识分支已经点亮；
- 哪些分支仍然缺失。

领域树主要使用 `is_a` 和 `part_of` 关系生成临时层级结构。例如：

```text
证券交易后处理
├── 交易确认
├── 交易清算
│   ├── 净额结算
│   └── 中央对手方
├── 证券交收
│   ├── 券款对付
│   └── 交收周期
└── 对账
```

底层数据仍然是图。一个节点存在多个上位概念时，领域树可以为当前视图选择一个主要展示父节点，同时以次要连接或跳转入口保留其他关系，不得复制正式节点。

#### 流程视图（Process View）

流程视图用于回答：

- 业务按什么顺序发生；
- 当前术语位于哪个环节；
- 它的上一步和下一步是什么；
- 哪些后续步骤依赖当前步骤的结果。

流程视图主要使用 `precedes`、`follows` 和 `depends_on` 关系，默认从左到右排列。例如：

```text
订单 → 成交 → 交易确认 → 清算 → 交收 → 对账
```

流程分支可以并列展示；发现循环或方向冲突时必须提示待校验，不能为了排成直线而静默删除关系。

### 7.2 视图选择原则

- 默认进入关系图；
- 用户可以主动切换关系图、领域树和流程视图；
- 系统可以根据当前关系类型推荐更合适的视图，但不得无提示切换；
- 切换视图时保持当前节点的选中状态；
- 三种视图共享节点详情、搜索、点亮和来源能力；
- 节点位置属于某个视图的展示状态，不属于节点知识本身；
- 用户手工固定的位置优先于自动布局。

## 8. AI 能力要求

### 8.1 术语提炼

AI 应优先抽取：

- 行业标准术语；
- 业务流程名；
- 系统或架构概念；
- 协议、机制和方法；
- 领域内常用缩写；
- 容易混淆且值得单独解释的概念。

系统不应把“系统”“流程”“问题”“实现”等普通词规范化为正式节点，除非它们在当前语境中组成了明确专业术语。

输入可能存在多义词。例如“清算”可能处在证券、支付或银行卡语境中。无法可靠判断时，系统应先展示语境选项或把节点标记为“待校验”，不得自行将某一语境当成事实。

### 8.2 中英文术语交叉验证

英文不能仅依赖逐字翻译。生成节点时，AI 应：

1. 先判断具体行业与语境；
2. 查询行业标准、监管机构、标准组织、权威技术文档或高质量专业资料；
3. 确认中英文术语在相同语境中是否对应；
4. 记录主要校验来源与访问日期；
5. 出现多个通行译法时，选择最常见或最权威的一项作为主名称，其余放入别名；
6. 无法充分验证时明确标记 `needs_review`，而不是伪造确定性。

资料优先级建议为：监管机构或标准组织 > 官方技术文档 > 权威行业机构 > 专业教材或论文 > 高质量行业文章。用户应能看到来源摘要，但来源不必占据节点主视图。

### 8.3 双语解释生成

中文和英文解释都应是领域内自然、专业、独立可读的文本。每个解释建议覆盖：

- 它是什么；
- 它解决什么问题；
- 它处于哪个业务流程或技术体系；
- 它如何运作；
- 它和相邻、易混术语的区别；
- 一个具体案例；
- 必要时说明地区、市场或技术实现差异。

英文版应采用真实工作场景中常见的专业表达，不要求逐句对应中文，但关键事实必须一致。

### 8.4 关系与建议节点生成

AI 应在以下时机更新关系：

- 新节点创建后；
- 节点领域或范围发生显著修改后；
- 用户主动点击“整理图谱”后。

建议节点应满足：

- 与至少一个已确认节点存在可解释的关系；
- 优先补充关键前置概念、后续流程、上位概念和易混概念；
- 单次默认生成 3～7 个，避免图谱迅速膨胀；
- 不直接生成完整长文，直到用户选择点亮；
- 不重复现有节点或其别名；
- 推荐理由可被用户查看。

## 9. 功能需求

### P0：第一阶段必须完成

#### FR-01 全局输入与历史

- 用户每次可以输入一个关键词并提交；
- 系统保留最近的原始输入、处理状态和对应节点；
- 提交失败时保留输入内容，可重新执行。

#### FR-02 术语规范化与语境确认

- 系统检查错字、别名、缩写和可能的规范名称；
- 明确纠错可以自动继续，但必须保留原始输入和纠正理由；
- 涉及专业含义差异时不得静默修改；
- 语境明确时不打断用户；
- 语境存在实质歧义时展示 2～4 个具体选项，等待用户选择后继续。

#### FR-03 节点自动补全

- 自动生成第 6 节规定的核心字段；
- 中英文名称与领域描述需要经过来源校验；
- 用户可在保存前编辑所有字段；
- 生成过程应显示阶段状态与失败原因。

#### FR-04 节点详情与编辑

- 并排或可切换展示中文、英文内容；
- 展示术语来源、AI 置信提示及更新时间；
- 支持单字段编辑和单字段重新生成；
- 用户编辑内容不得被后续自动更新静默覆盖。

#### FR-05 图谱视图

- 显示节点和有方向、有类型的关系边；
- 支持拖动、缩放、聚焦、搜索和打开节点；
- 已点亮与未点亮节点视觉状态不同；
- 支持以某个节点或某个具体领域为中心查看局部图谱；
- 大图默认只渲染当前邻域，避免信息过载；
- 默认提供以当前节点为中心的一至两层关系图；
- 支持在关系图、领域树和流程视图之间切换；
- 领域树仅投影 `is_a` 和 `part_of` 等层级关系；
- 流程视图仅投影 `precedes`、`follows` 和 `depends_on` 等过程关系；
- 切换视图不得复制节点或修改底层关系。

#### FR-06 自动关系编排

- 保存节点后，AI 分析其与现有节点的关系；
- 用户可确认、修改类型或删除关系；
- 提供“整理当前图谱”触发入口；
- 布局变化不得改变关系数据本身。

#### FR-07 未点亮节点

- AI 可在局部图谱中添加建议节点；
- 显示推荐理由和预期关系；
- 用户可以点亮、忽略或隐藏建议；
- 被忽略的建议在相同上下文中不应反复出现。

#### FR-08 搜索

- 支持按中文、英文、别名和缩写搜索；
- 搜索结果展示领域和范围，帮助区分同名术语；
- 搜索可定位到节点详情或图谱位置。

### P1：第一阶段完成后考虑

- 批量导入关键词；
- 节点版本历史和内容差异对比；
- 按领域导出双语术语表；
- 学习状态，例如“待了解、理解中、已熟悉”；
- 基于图谱自动生成学习路径；
- 通过聊天继续追问某个节点；
- 将稳定领域抽象为领域节点；
- 图谱快照、分享和导出；
- 领域树和流程视图的高级布局、折叠及跨层级跳转。

## 10. 页面与交互建议

第一阶段可采用四个主要界面：

1. **收集页**：以大输入框为中心，展示最近输入和处理中任务。
2. **语境确认抽屉或页面**：仅在术语存在实质歧义时展示，完成语境选择或规范名称确认。
3. **节点详情页**：展示双语字段、案例、关系、来源和编辑入口。
4. **图谱页**：默认查看局部关系图，并可切换领域树和流程视图；同时支持整理关系、处理未点亮节点。

图谱页应提供一个明确的“AI 整理”入口。触发后先展示变更预览，例如“新增 4 条关系、推荐 3 个节点、调整 1 条关系类型”，由用户确认后写入，避免图谱在后台无感变化。

## 11. 示例

### 11.1 用户输入

> 交收

### 11.2 规范化与语境结果

| 原始输入 | 规范中文 | 专业英文 | 具体领域 |
| --- | --- | --- | --- |
| 交收 | 证券交收 | Securities Settlement | 证券交易后处理 |

如果用户只输入“清算”，而当前知识库同时包含证券交易和支付系统内容，系统应先询问本次是“证券交易清算”还是“支付清算”。如果输入“日切”，系统应提示专业英文高度依赖具体系统和公司用语，而不是强行给出唯一译法。

### 11.3 可能关系

- 交易清算 `precedes` 证券交收；
- 证券交收 `depends_on` 交易清算结果；
- 日切 `related_to` 当日交易批处理与账务日期切换，但不一定是清算到交收流程中的固定前后节点。

### 11.4 可能的未点亮节点

- 交易确认 / Trade Confirmation；
- 中央对手方 / Central Counterparty（CCP）；
- 券款对付 / Delivery versus Payment（DvP）；
- 交收周期 / Settlement Cycle；
- 对账 / Reconciliation。

## 12. 非功能需求

- **可追溯性**：AI 生成的专业术语和关键事实应尽可能附带来源及访问日期。
- **可修订性**：所有 AI 生成内容均可编辑；用户内容优先级最高。
- **一致性**：中英文版本的关键事实、案例结论和关系方向保持一致。
- **响应反馈**：长时间生成必须提供进度状态，不让用户误以为系统卡住。
- **局部加载**：图谱按邻域加载，首屏不应加载所有节点。
- **数据安全**：节点默认仅用户本人可访问；日志不得记录不必要的完整私有输入。
- **可迁移性**：数据模型应支持未来导出 JSON 或其他通用格式，避免锁死在单一图形组件中。

## 13. MVP 验收标准

第一阶段可在满足以下条件时视为可用：

1. 用户输入一个关键词后，系统可以完成规范化和语境判断；语境明确时自动继续，存在实质歧义时才请求选择。
2. 生成后的节点包含中英文术语、具体领域与范围、双语长解释、双语案例和日期。
3. 系统能处理多义或无法可靠翻译的词，并显示待校验状态，不伪装成确定答案。
4. 节点中可以查看术语校验来源，用户可以修改 AI 生成内容。
5. 两个以上节点之间可以生成并展示带类型、方向和说明的关系。
6. 用户可以手动触发图谱整理，并在写入前预览 AI 建议的变更。
7. 图谱能以不同样式展示已点亮和未点亮节点。
8. 用户可以把未点亮节点转为正式节点，也可以忽略建议。
9. 支持使用中文、英文、别名或缩写查找已有节点。
10. 用户已编辑字段不会被 AI 后续操作静默覆盖。
11. 关系图默认以当前节点为中心，只加载一至两层邻居，并保持已点亮与未点亮节点的视觉差异。
12. 同一份节点和关系数据可以投影成关系图、领域树或流程视图，切换视图不会产生重复节点或改变知识事实。

## 14. 待后续决策

以下问题不阻塞需求确认，但需要在进入详细设计时决定：

- 节点内容是保存生成时的静态版本，还是允许定期重新校验行业定义；
- 是否需要独立的“掌握程度”，以及它与“已点亮”的区别；
- 领域是否在数据稳定后升级为可连接的独立节点；
- 来源校验采用实时联网检索、限定资料库，还是两者结合；
- 是否允许同一术语在不同领域分别建立节点，例如支付清算与证券清算；
- 英文内容采用偏全球通用表达，还是允许选择美国、英国、新加坡等市场语境。

## 15. 推荐的第一阶段实施顺序

1. 定义节点、关系、输入记录和来源记录的数据模型。
2. 完成单关键词输入、术语规范化、必要的语境确认和节点生成闭环。
3. 完成节点详情、双语编辑、来源展示与搜索。
4. 实现关系生成、关系确认和局部图谱。
5. 实现未点亮节点、点亮流程和忽略机制。
6. 增加“AI 整理”变更预览、异常处理和生成质量评估。
